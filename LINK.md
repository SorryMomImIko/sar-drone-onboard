# Кадр находки и координаты на землю

Телеметрия с полётника описана отдельно, в `MSP_BETAFLIGHT.md`.

На землю уходит **тот самый кадр, на котором сработал детектор**, с рамкой,
классом и уверенностью, плюс метка с координатами. Задымление (класс 2) —
такая же находка, как человек; подтверждение считается по каждому классу
отдельно.

## Почему одного TCP для гарантии мало

TCP гарантирует доставку **внутри соединения**: пока оно живо, ядро само
переспрашивает потерянные пакеты. Но на дроне канал рвётся постоянно, а
`send()` возвращает успех, как только данные попали в буфер ядра, — не когда
они дошли. Оборвалась связь на середине кадра — отправитель не знает, сколько
успело уйти. Поэтому поверх TCP добавлены три вещи:

1. **Очередь на карте платы.** Находка сначала ложится файлом в `queue/` и
   только потом отправляется. Запись идёт через временный файл с `fsync` и
   переименованием, так что при снятии питания в очереди не окажется
   обрезанной записи.
2. **Подтверждение от земли.** Запись удаляется из очереди, только когда
   земля прислала ACK с её номером. Земля отправляет ACK **после** записи на
   диск и `fsync`, а не до.
3. **Переотправка.** При переподключении всё неподтверждённое уходит заново,
   в том же порядке.

Итог: находка переживает обрыв связи, перезапуск программы и снятие питания
с платы. Теряется она только вместе с картой памяти.

## Кто к кому подключается

Дрон — клиент, наземная станция — сервер. Дрон подключается сам и
переподключается каждые 3 секунды после обрыва, поэтому сервер запускается
один раз до взлёта и работает. Когда отправлять нечего, раз в 10 секунд уходит
проверка связи: молчащее TCP-соединение может быть мёртвым часами, ядро об
этом не скажет.

## Формат записи

TCP — это **поток байтов**, границ сообщений в нём нет, поэтому длина пишется
явно (та же причина, что и при разборе MAVLink с UART):

```
0..3   "SARL"
4      версия = 1
5      тип: 0 = проверка связи, 1 = кадр, 2 = вырезка, 3 = метка JSON
6..9   номер записи seq      <- по нему приходит подтверждение
10..13 номер события event_id
14..17 длина данных
далее  данные
```

Ответ земли: `"SARA"` + seq, восемь байт.

Метка уходит **раньше** кадра: координаты весят сотню байт и на узком канале
дойдут за доли секунды, кадр — за секунды. Оператор узнаёт «где» сразу,
картинка догоняет.

## Отдельный поток

`send()` по TCP на узком канале блокируется на секунды, когда буфер отправки
полон. В потоке инференса это означало бы пропущенные кадры. Поэтому инференс
только кладёт файл в очередь и идёт дальше (`link.enqueue`, не блокируется),
а отправкой занимается поток внутри `ReliableLink`.

## Что проверено

Пять сценариев, все прогнаны на настоящих сокетах с настоящим JPEG:

| Сценарий | Результат |
|---|---|
| Сервер запущен, обычная отправка | 2 записи доставлены, очередь пуста, кадр байт в байт |
| Сервера нет, находки копятся | 2 записи лежат в `queue/`, ничего не потеряно |
| **Обрыв ровно на середине кадра** (посредник рвал связь после 4000 из 11 079 байт) | переподключение, переотправка, на земле **один** целый файл |
| Программа перезапущена, сервер поднялся позже | очередь пережила перезапуск, всё доставлено |
| Подтверждение потеряно, находка пришла дважды | земля узнала повтор, в журнале **одна** строка |

Последний сценарий закрывает дыру, которая была до него: без защиты от
повторов на карте появлялись бы две метки об одном человеке.

## Приёмник на земле

```sh
python tools/ground_server.py --port 5700 --dir rescue_17oct
```

Стандартная библиотека, ставить нечего. Пишет `event_NNNNNN_frame.jpg` и
`events.jsonl`, отбрасывает повторы (в том числе после своего перезапуска —
при старте читает, что уже принято).

## Что настроить

```cpp
static const std::string GROUND_STATION_IP   = "192.168.1.100";
static const uint16_t    GROUND_STATION_PORT = 5700;
static const std::string QUEUE_DIR           = "queue";
static const bool        SEND_FINDING_FRAME  = true;    // кадр с рамкой
static const bool        SEND_FINDING_CROP   = false;   // + вырезка крупным планом
```

Размер кадра: 800 пикселей по ширине, качество 65, ~11 КБ. В исходном размере
было бы 63 КБ. Таблица замеров — в `FindingImage.hpp`. При узком канале
уменьшать ширину до 640 (6.5 КБ), и только потом трогать качество.

**Подписи только латиницей.** `putText` из OpenCV не умеет кириллицу.

## Чего по-прежнему нет

TCP требует **IP-сети**. WiFi, LTE и цифровые видеолинки её дают, а
телеметрийные радиомодемы (SiK, RFD900x) — нет: там последовательный поток
байт. На таком модеме нужен либо PPP поверх последовательного порта, либо
упаковка записей в MAVLink-сообщения `TUNNEL`. Очередь и подтверждения при
этом остаются как есть — меняется только транспорт под ними.

Файлы `UdpSender.hpp`/`.cpp` и `ImageTx.hpp` остались в проекте, но больше не
используются: `main.cpp` на них не ссылается.

# Модель под NPU RK3566

## Файлы

| Файл | Что это |
|---|---|
| `best_i8_split.rknn` | рабочая модель, int8, 4.2 МБ — её грузить на плату |
| `best_fp_split.rknn` | та же модель в fp16, 7.4 МБ — запасной вариант, точнее и медленнее |
| `librknnrt.so` | рантайм RKNN 2.3.2 под aarch64, кладётся в `/usr/lib` на плате |
| `make_rknn.py` | воспроизведение всей конвертации с нуля |
| `compare_split.jpg` | сверка детекций fp16 против int8 на 15 кадрах |

Калибровка: 296 кадров (100 дым, 40 чистый лес, 59 sard, 58 ladd, 39 visdrone),
letterbox 640x640, заливка 114 — файлы в `calib/`, список в `dataset.txt`.

## Выход модели изменился: два тензора вместо одного

Было (стандартный экспорт): `output0` = `[1, 7, 8400]` — рамки и вероятности вместе.
Стало: `[1, 4, 8400]` (cx, cy, w, h в пикселях входа 640) и `[1, 3, 8400]` (вероятности
person / car / smoke, уже после sigmoid).

Это не прихоть: при общем тензоре квантизация берёт масштаб по рамкам (значения до 640),
и вероятности 0..1 полностью теряются — int8-модель выдаёт ноль детекций. Проверено.

### Что поправить в `RknnYolo.cpp`

Декодер сейчас рассчитан на один выход `[1, 4+nc, 8400]`. Нужно:

1. `rknn_outputs_get` на **два** выхода вместо одного.
2. Рамки читать из выхода 0 (4 строки), вероятности — из выхода 1 (3 строки),
   индексируя обе по одному и тому же якорю `i` из 8400.
3. Sigmoid к вероятностям применять **не нужно** — он уже внутри графа.
4. DFL-декод тоже не нужен — рамки уже в пикселях входа 640.

Остальное (letterbox, пересчёт в координаты исходного кадра, NMS, фильтр
подтверждения) не меняется.

### Ещё одно расхождение

В README пайплайна указан `target_platform='rk3588'`. На плате RK3566 — модель,
собранная под 3588, не загрузится. В `make_rknn.py` уже стоит `rk3566`.

## Установка на плату

```bash
sudo cp librknnrt.so /usr/lib/
sudo ldconfig
# проверка драйвера (на плате стоит 0.9.7, рантайм 2.3.2 с ним совместим)
sudo dmesg | grep -i rknpu | head -3
```

Модель кладётся рядом с исполняемым файлом пайплайна, путь задаётся
через `MODEL_PATH` в `main.cpp`, там же `NUM_CLASSES = 3`.

## Что ожидать по скорости

Сейчас на CPU: 6.23 с/кадр при входе 960 (0.16 fps).
На NPU при входе 640 ожидается 10-15 fps чистого инференса, 8-12 fps с учётом
препроцессинга и NMS на CPU. Проверять замером, а не верить оценке.

## Что проверить после первого запуска

int8 в симуляторе совпал с fp16 с точностью до 0.02 по уверенности, но на мелких
целях (ladd — люди с большой высоты) счётчики расходились: 1 против 2 и 3 против 5
обнаружений у порога 0.25. Это нормальный разброс квантизации на грани порога,
но пороги `conf_thresh` стоит перепроверить на своей валидации, а не переносить
вслепую из `predict.py`.
